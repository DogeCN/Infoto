## 上传进度：区分「能否测量」与「能否显示」

用户提问「图片 transcoding 有可测量的粒度吗」，追到 v1 初版对比后又问「哈希那段接上是不是还得手调权重」。两轮追问暴露了第一轮答错的地方。

### 结论：图片转码**没有**可测量的粒度，v1 的「细」与图片无关

- `image.worker.ts` 只有三步，每步都是一次性调用、不发事件：`createImageBitmap` → `drawImage` → `convertToBlob`。
- v1 的粒度全部来自别处：视频按帧计数（半真，分母是估算，`0.01+0.49*x` 是手调权重）、上传按字节（真）、批次总进度（纯合成）、以及 `stepLabel` 步骤文案（文字粒度最便宜，也最能掩盖数字在该段毫无意义）。
- **关键**：v1 图片压缩期间 `prepP` 恒为 0（`task.js:165-170` 只设了 `stepLabel`），所以纯图片批次的进度环**钉死 0%**。

### 权重的本质

同量纲单一比值（帧/帧、秒/秒、字节/字节）天生客观，不需要告诉任何人「哈希这步算 15% 还是 20%」。**权重只在「把不可比的量加到一起」时出现。**

### 踩坑：hashing + 落盘是**一个 tee 循环**，且不是 transcoding 的延续

- `opfs.ts#storeArtifact` 把 OPFS 写流喂给 `hash.ts#teeToHash`，同一 `for(;;)` 里 `await write` → `hasher.update` → `bytes +=`。
- ⚠️ **第一轮把三阶段说成「转码→哈希→落盘」并暗示可以拿哈希的进度报转码，这是错的**，用户顺着这个误解提了第三个需求。第二轮才纠正。
- 教训：**判断「能不能复用某条流水线的进度」时，先确认数据是不是真的在流动**。同一个 `bytes` 计数器存在，不等于它在另一条腿里已经在跑。

### 改动

1. **视频 transcoding 起始不再钉 0%** — `pumpVideoLeases` 不传 fraction；`videoProgress` 分支滤掉 `fraction === 0`（mediabunny 首个 tick 是「已启动未完成」，GIF 首 tick 恒为 `1/frameCount`，所以滤 0 安全）。`uploading` 起始的 `fraction: 0` 保留 —— 那是诚实起点。
2. **hashing 腿接上真实字节 fraction**（用户明令：不新增前端元素，只改进度上报）
   - `teeToHash(source, write, onBytes?)` → `storeArtifact(…, onBytes)` → SW `notifyBytes(rec, total, written)`
   - `App.svelte#PANEL_STAGES` 加 `'hashing'`；`pendingPhotos` 不动
   - `UploadPanel.indeterminate` **不用改**（`fraction == null` 已覆盖）
3. **决策记录**：`.ai/adr/0002-progress-only-real-measurements.md`

### 瀑布流：列数而非像素

`band=260` 是绝对像素，在 320px 下 `round((308+12)/(260+12)) = 1` 列；而滑块 `min=200` 到不了三列所需的 148px。**模型错了，不是默认值没调好。**

- 新增 `web/src/base/lib/band.ts`（纯函数）：`bandForCols` / `colsForCross`（低于 120px 自动降列）
- `layout.band` → `layout.cols`（默认 2），`SETTINGS_VERSION` 1 → 2，v1 blob 整体丢弃
- **缩放改为整体缩放**：`gap * zoom` 和 `band * zoom` 一起走（原来只缩 band 会让 gap 占比翻倍、列数在缩小途中改变）

### 顶栏：实测优先于断点

用户三轮反馈：「435-480px 频繁抖动」→「368px 以下右三个按钮看不到但箭头也没显示」→「现在动态收缩没问题但变宽不能展开回去，两个方向都要测」→「467-483 仍抖，374 以下箭头没显示」→ 第二屏按钮改右对齐 → 「767-769 有高度跳变」。

**我连续三轮修错了对象。** 决定性证据：

```
496a: full    A=257   ← 槽位测出带标签宽度
496b: compact A=215   ← 同一槽位，几帧后测出另一个值
```

`A` 就是 `invisible absolute` 的测量副本 —— 绝对定位的 `offsetWidth` 相对**包含块**收缩，标签变体被裁成 215（真实 258）、纯图标 149。**差 42px，所有阈值全错。判据再对，输入是假的也没用。**

四个坑（已全部写入 `MEMORY.md`）：

1. `absolute`/`fixed` 测宽需 `w-max` 才是内容宽
2. 探针放 header **内部**会成为 `w-[200%]` 轨道的包含块，把两屏拖出屏幕 → 移到外部
3. `visibility: hidden` **可被后代覆盖**（真有个箭头画在视口原点）→ 改 `opacity-0` + `pointer-events-none` + `inert`
4. **`clientWidth` 不是响应式源**，`$derived` 里只算一次（曾冻在 64px）→ 必须由 `ResizeObserver` 写进 `$state`

两个判据设计：

- **`"装得下"是错的问题** —— 需求恰好满足时 `flex-1`spacer 被压到 0px（实测 483px 时`slack: 0`），离溢出只差一个亚像素。加 `BAR_MIN_SLACK_PX = 12`。
- **迟滞必须双向不对称** —— 变紧用余量，变宽用 `BAR_HYSTERESIS_PX = 24`。把两者混成「当前模式还有没有余量」会让**降级后永远升不回来**（已降级的模式当然总是有余量）。这个 bug 只在**测试变宽方向**时暴露。

### 768px 高度跳变 + 浮点数

实测 `767px: 55px/24px → 768px: 63px/48px`，高度和 padding 同时跳（`h-14 md:h-16` + `px-3 md:px-6`）。

- **padding 改为常量** `BAR_PAD = 12`（用户明令「不应该动 padding」；`px-6` 在桌面太宽，把控件推离窗口边缘）
- 高度改 ramp，区间**拉长**到 480→1600（8px 摊到 1120px → 每 ~140px 动 1px）
- **高度不取整**：有效级数 = `8 × dpr`。参考真机 dpr 3.375 → 27 级而非 8 级，round 掉就把多出来的全扔了。dpr=1 桌面光栅化会丢弃小数，等于没变也不会更差。

### 飞箭头

- **箭头必须常驻两屏**（第一屏最右、第二屏最左）—— 放在单屏会让另一屏无法切换。这是实测发现的设计遗漏。
- 第二屏：箭头靠左 + `flex-1` + 三按钮**贴右**
- `rotate-180` 与轨道共用 `--duration-enter/--ease-enter`，转动时刻正好是飞抵时刻

## Lightbox 音量按钮 + 媒体加载：一轮完整的负面改动与修正

用户诉求分三次提出，每次都指向真问题，但我的前两轮修复**都是无效的**。

### 时间线

1. **「按钮应和瀑布流一致，放卡片内右下角」** —— 原按钮挂在视口（`bottom-24 right-5`）。第一版加了一层 `.lb-frame` 定位框，抄 `.lb-skeleton` 的尺寸公式。
2. **「位置和缩放都有问题」**（截图）—— `.lb-frame` **只抄了 `width`/`max-height`、没给高度**，框高恒为 0，按钮贴在**视口垂直中线**上。整层删除，改为给 `wrapEl` 加 `relative` + 按钮 `absolute; right/bottom: 0.5rem`。同时发现缩放时按钮被一起放大，加 `--inv = 1/scale` 反缩放。
3. **「放大后按钮反而突然缩小了」** —— `--inv` 瞬时生效而 wrapper 的 `scale` 走 200ms 过渡 → 过渡第一帧按钮已缩一半。`applyWrap` 把同一 `transition` 字符串写给两个元素。
4. **「切到视频仍有加载骨架 + 首帧尺寸错」** —— 真因是 `<video>` 无 `width`/`height` **属性**时按 CSS 替换元素默认 **300×150** 布局。补了属性。
5. **「切邻居仍有加载动画」**（25MB 视频截图）—— 加了 `<link rel=preload as=video>`，无效（它下整个文件）；改 Range 预热首段 2MB，**也无效**。
6. **「本轮改动后圆角没了、按钮错位、依然能截到加载，是完全的负面改动」**（三张截图）—— `width`/`height` 属性是**呈现尺寸**不是固有尺寸：它设了 `width: 1920px`，CSS 只能收缩，高度不再按比例跟随 → 圆角被裁、按钮错位。

### 最终形态

- **`.lb-box` 单一尺寸公式**，`.lb-media` 与 `.lb-skeleton` 共用（`width: min(--w, 视口预算, 高预算 × var(--ar))`），彻底消除影子副本。属性全部撤掉，只留 `--w` / `--ar`。
- `<video>` 加 `preload="auto"`，**不手工预取**。冷缓存实测：first visible 87ms、骨架 3 帧。
- 切图时**不清空 `loadedUrl`**（预热命中时清空等于在已就位的媒体上盖骨架）。

### 我犯的三个方法错误（本轮最贵的部分）

| 错误                                           | 后果                                                     | 修正                                        |
| ---------------------------------------------- | -------------------------------------------------------- | ------------------------------------------- |
| curl 首次命中 CDN 缓存，把 29MB/s 报成 2.5MB/s | 推出「25MB 要 10 秒」的结论 → 「物理必然」→ 错误优化方向 | 同一 URL 至少测两次；差一个数量级先怀疑测量 |
| 同一浏览器会话内反复切，文件早进 HTTP 缓存     | 「first visible 24ms」是缓存命中，**被测改动从未被执行** | 每次 A/B 用全新 browser context             |
| 用 0.3MB 的视频验证预加载                      | 秒开，**掩盖了 25MB 的真实问题两轮**                     | 永远测最坏情况的资源                        |

另有一个 harness 陷阱：`page.mouse.click` 点在视口外**静默无效**（瀑布流大量卡片 `boundingBox().x = -316`），我一度以为 Lightbox 点不开。`.will-change-transform` 也不唯一于 Lightbox，判别要用 `.lb-meta`。

### 教训

- **`width`/`height` 属性是呈现尺寸**，会脱离 `aspect-ratio` 单独生效；凡是依赖比例的布局，必须全程用 CSS 表达。
- **优化前先算 ROI**。为 0.5s 收益写了 50 行预热逻辑，而预热本身要 0.43s —— 净收益为零。
- **被测环境与真实用户环境的差距要显式消除**（冷缓存、真实文件、真实视口），否则「验证通过」只证明 harness 自己能通过。

## 三处 UI 修正：Tooltip 翻译 / 语言轮换按钮 / Toast 避让底栏

### 1. Tooltip 切语言后不翻译 —— 模块级快照

`SettingsPanel.svelte` 的 `TYPE_LABELS` 是**普通 `const`**，在组件初始化时就把 `copy.settings.typeImage` 求值冻结了，切语言后三个类型开关的 tooltip 仍停留在旧语言。改 `$derived` 即可。全仓扫描确认**仅此一处**（`grep "const X = copy\."` 无其他命中）。

> 这与「模块级常量表会冻结语言」是同一条规律的两个面：模块级 `const` 和组件级 `const` 都会快照，只是后者更隐蔽——它看起来「在组件里」，直觉上以为会跟着重渲染。

### 2. 语言选择：`<select>` → 单个轮换按钮

理由：只有两种语言时下拉是过度设计；轮换还能让**标签始终用自己语言显示**（用户总能认出当前在读哪种语言）。按钮 = 地球图标 + 当前语言名 + 右侧 `RefreshCw` 轮换提示，整行等宽与上方滑块对齐，单一语言时 `disabled`。

新增 `settings.languageSwitchHint`（中英各一条）。

### 3. Toast 避让底栏 —— 写死的 offset 是错的

原 `offset={{ bottom: '4.5rem' }}` 是为多选条留的**常量**。但多选条只在多选时出现（且与上传浮层互斥），所以**平时白留 4.5rem**，toast 悬在离底边 4.5rem 处。

改为 `$derived`：

```
multiMode                      → 4.5rem   // 多选条：全宽 bottom-0，z-40
panelRows>0 && !wideLayout     → 5.5rem   // 上传浮层：窄屏全宽贴底
否则                            → 1rem     // 贴边
```

**桌面端上传浮层在 `md:right-4 bottom-4`（右下），toast 在左下，不冲突，所以 `!wideLayout` 这个条件是必要的** —— 否则宽屏上传时 toast 会莫名上浮。六个分支枚举验证：多选 4.5rem / 窄屏上传 5.5rem / 其余 1rem，多选时 toast 底边 728px 恰好高于多选条顶边 735px。

`wideLayout` 用 `matchMedia('(min-width: 768px)')` + `$effect` 订阅（与 UploadPanel 的 hover 判定同源）。

### 验证

- Tooltip：切换前 `"Reset layout"` → 切换后 `"重置布局"`（英文侧同样验证过 `"Reset filters"` → `"重置筛选"`）

## 语言按钮收尾 + Toast 避让的三个后续修正

用户验收后提出三点：删 `languageSwitchHint`；多选底栏避让改 5rem；**移动端避让上传浮层要动态随浮层浮动**（浮层高度随行数变化，写死的 5.5rem 在 1 行时留白过大、行多时会盖住）。

tooltip 回到纯 `copy.settings.language`。轮换箭头（`RefreshCw`）本身已经表达了「点击切换」，tooltip 不必复述。

### 2. 多选避让 4.5rem → 5rem（80px）

### 3. 上传浮层避让改为实测高度

- `UploadPanel` 新增 `onHeight?(px)` prop：对**内层卡片**（不是带 `inset:-8px` 外扩的 wrapper，那会多量一圈）挂 `ResizeObserver` 上报 `offsetHeight`。
- **RO 而非「行数变化时测量」**：盒子还会因折叠、安全区 `env(safe-area-inset-bottom)`、入场过渡而变，行数对这些一无所知。
- ⚠️ **effect 必须依赖 `hidden`**：translate 不改变 `offsetHeight`，所以从 hidden 回来时 RO 不会触发，高度会**卡在 0**。把 `report` 写成读 `hidden ? 0 : offsetHeight` 并让 effect 依赖两者。
- ⚠️ **App 侧的回调必须是模块级 `const`**，不能内联箭头——`UploadPanel` 的 effect 依赖 `onHeight` prop，父组件每次渲染都给新引用会**把 ResizeObserver 拆了重建**。
- 单位用 **px 不用 rem**：浮层高度是实测值，经根字号换算会在测量和使用之间插一层换算。

验证：逐帧同时记录面板盒高与 sonner 的 `--offset-bottom`——32 帧两者同屏，`offset = 61px` = **45(实测面板) + 16(边距)**；面板离场后 offset 回落 16px。多选时 80px，toast 底边 720 高于多选条顶边 735。

### harness 备注

- sonner 的 Toaster DOM **只在有 toast 时存在**，无法从空闲页面读回 offset——要么造一个 toast（上传 `.txt` 走 accept 拒绝路径，零副作用），要么验算 `$derived`。
- 触发 toast 的可靠零副作用路径：`page.setInputFiles('input[type=file]', '非媒体文件')` → accept 校验拒绝并 toast，不写库。
- 逐帧 trace 若横跨「切走」过程，`skeleton? true` 会被算进来——判据限定在目标状态的连续区间（此坑第二次踩）。
- 本轮确认 photos 22→24 的 +2 是**用户自己 11:54 上传**的两张（种子域名 URL），非测试写入。
