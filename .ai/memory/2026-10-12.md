# 2026-10-12

## 公告编辑上传的三个阶段，其实是同一个 bug

用户报了三件事：默认尺寸骨架、上面盖着丑陋文件名；尺寸改变、图片不适配；才变成真实尺寸。三条症状，一个根因。

### 根因：占位比例是猜的，而尺寸本来就能提前拿到

编辑器**上传完成后才插入 markdown**（`MarkdownEditor.pickImage` 里 `await onPickImage()` 之后才
`insertMediaAt`）。所以整个上传期间预览里根本没有可测量的东西，而 `.md-media` 硬编码
`aspect-ratio: 16 / 10` 兜底，直到浏览器在 load 事件里报出 `naturalWidth/Height` 才改成真实比例。

于是三个阶段分别是：16:10 猜测 → 图片解码时跳到真实比例 → 真实尺寸。所谓"丑陋文件名"是
**alt 文本**——图片解码前浏览器会把 alt 当替代文字画出来（`MarkdownEditor` 当时把去掉扩展名的文件名
塞进了 alt）。

### 修法：复用瀑布流早就在用的 `probeSourceSize`

关键发现：**尺寸一直可以直接拿到**。`probeSourceSize` 就是干这个的（图片 `createImageBitmap`，
视频 `videoWidth/Height`），瀑布流用它给乐观卡片占位，而编辑器从来没调用过。

现在 `AnnouncementEditorDialog.pickImage` 在选中文件的那一刻就 `URL.createObjectURL(file)` +
`probeSourceSize(file)`，预览面板用**实测比例**预留盒子。这里本地预览是诚实的——编辑器那条腿
原样上传不转码，手里的字节就是托管 URL 将要提供的字节；这一点在相册那条转码腿上不成立。

`isImageFile`（新增）按 **MIME 或文件名**判定：Windows 选文件经常 MIME 为空，那种情况不预览
比"类型不准"更糟。

### 实测

整个上传过程每 0.9s 采样一次：

- 600×300 横图 → 全程 **648×324**，比例 `600 / 300`
- 300×900 竖图（位移最大）→ 全程 **648×1944**，比例 `300 / 900`
- `alt` 全程为空，上传完成后 markdown 插入 `![](url)`

旧路径下那张竖图会从 16:10 跳到 1:3——三个阶段里最刺眼的就是它。

### 顺带清掉的死代码

`uploadName` 这个 prop 只用来喂 alt，alt 去掉后它整条链路（dialog state → prop → 两处使用）都
没了。

### 一次绕路

第一次写探针时把文件输入框当成 `nth(0)`，实际那个是 SQL 导入用的（`accept=".sql"`）；编辑器的是
`nth(2)`。而且编辑器的 `pickImage` 是自定义 promise + `input.click()`，`setInputFiles` 直接绕过了
它——必须真的点工具栏那个 File 按钮、在 `filechooser` 事件里塞文件。另外 SharedWorker 直连
`127.0.0.1:8788`，**不走 Playwright 的 route 拦截**，所以本地图片主机必须真的起来，否则
上传必然 Network error。这两条对以后写编辑器探针都适用。
