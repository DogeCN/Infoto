## Corrections to operator assumptions (verified in code)

- "服务端没 id36 代理" is not accurate: `GET /l/:id36` **is** the server-side proxy; a
  pending (unsynced) upload simply has no server id yet, so the Lightbox hides the
  id-addressed actions (`isPending` gate) — copy-original only.
- Deleting a pending photo does **not** clear the queued upload op. The oplog is
  append-only (`engine.addOp`); the delete queues a `delete` op after the `upload` op, the
  server applies both in order, and the media-host artifact is orphaned. Admin-only
  (`selfId === 0`). Actual op cancellation would need an engine-level remove-by-sha before
  first sync — not built.

## Multiplexing findings

Transport-level multiplexing already exists: the browser talks HTTP/2 to Cloudflare, and
the SharedWorker's image pool (`imagePoolSize` from hardwareConcurrency/downlink) runs
several transcode+upload jobs concurrently over that one connection. Request count per
upload is already minimal: exactly one `POST /upload` per artifact, no HEAD preflight, and
the CORS preflight is cached for a day (`Access-Control-Max-Age`). Batching multiple
artifacts into one multipart request would save requests only at the cost of per-file
progress, retry granularity, and the facade contract — not worth it unless real quota
pain shows up. View-side requests are already absorbed: `/l/:id36` answers
`Cache-Control: public, max-age=31536000, immutable`.
