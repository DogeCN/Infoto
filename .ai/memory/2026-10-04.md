## Review of the uncommitted change set, and what it turned out to need

Reviewed the working tree before committing it. It was a large single-sitting change: a shared
glitch glyph extracted into `src/shared/glitch.ts`, `.ai/CONTRACT.md` written from scratch, a
`designTokens.test.ts` gate, Lightbox rotation/pinch/double-tap, a waterfall FLIP fix, and a

**Gates were red on arrival**: `npm run lint` failed prettier on the two iris files and
`npm test` failed 4 of 8 iris tests. `ts-check` and `build` were green.

### Findings, and which were real

- **The iris was dead code** — 95 lines with a 135-line test, zero importers. Confirmed by the
  contract's own ⚠️ §4.4, which said "do not stack a fourth layer" about exactly this kind of
  extraction. Dropped, both files.
- **Three of the four failing iris tests were broken assertions, not bugs**: `"1.23px 4.56px"`
  parsed with `Number()` gives `NaN`; a sector-sum expectation was missing a `BLADE_COUNT`
  factor; and the scale-proportionality assertion compared `f(x)` against `f(2x) * 2`. The
  fourth — the leaf edge "jumping" 1.12px — is real but harmless: `leafRadius` has a vertical
  tangent at its angle clamp by construction, and the polygon is sampled at 7 points and never
  interpolated, so the kink cannot render. **The module's doc comment and its test both claimed
  a property the geometry does not have and does not need.**
- **`Lightbox.clampPan()` measured a stale rect** (see below) — the one substantive bug.
- **The error page's typography regressed** when the glyph was shared: `.gf` pins Inter and
  `font-weight: 800`, but neither font query ships 800, so the standalone page rendered
  synthetic bold _and_ dropped the real Space Grotesk 700 it used to show. Fixed by moving the
  glyph to 700 and adding `Inter:wght@400;700` to `ERROR_FONT_QUERY`. Lesson in §4.8.
- **`geomMemory` was typed `Map<number, LayoutBox>` but stored `{x,y,w,h}`** — no `id`. TS
  cannot catch it because `Map`'s methods are bivariant, so `Map<number, LayoutBox>` is
  assignable to `Map<number, GeomStamp>`. Added `GeomStamp = Omit<LayoutBox, 'id'>` to
  `base/lib/layout.ts` and used it in both files.
- **`FLIP_WINDOW_MS = 480` was `ca1b082`'s mistake repeated**, one commit after ADR 0015 was
  written to name it. Now `reflowFlipWindowMs` in `motion.ts`, derived from
  `--duration-reflow` at module load (not per card — `motionMs` calls `getComputedStyle` and
  cards mount on every scroll step). `motion.test.ts` asserts only that the window outlasts the
  animation.
- **A stale comment survived its own deletion**: `PhotoCard.svelte` still said "Media that
  will not load reads as 404 — the same glyph the not-found page uses" in the same diff that
  removed the 404 glyph.
- **`untrack()` at component init is not a no-op.** I removed it as one; `svelte-check
--fail-on-warnings` then flagged `state_referenced_locally` on all four geometry props.
  It is the documented way to mark a deliberate one-time read. Left in place, comment corrected.
- **The entrance animation on the error page's status code was an unintended casualty** of
  `.code` → `.gf`. Restored on the `.gf` container so the stack rises as a unit.

### The thing that cost the most time: a concurrent writer

Partway through, `Lightbox.svelte` was rewritten by another process **every few seconds** — and
`read` results went stale underneath me (an `edit` was refused with "file changed since it was
read"). Sampling mtimes over 12s showed writes at 01:02:40 and again at 01:02:48. A parallel
session had also added `base/lib/lightboxEngine.ts` and a 205-line `lightboxEngine.test.ts`, and
was mid-way through wiring them into the Lightbox.

**Do not begin a large rewrite of a file whose mtime is moving.** An `edit` refusal on a file
you read seconds ago means the file is not yours; check the mtime before re-reading and
re-applying, or two writers will interleave and lose work. Recorded in CONTRACT.md §5 gap 4.

The parallel session's output was good and was kept. One correction was needed:
`ctrlZoomTransform` returned `rot: 0`, which would silently un-rotate the image on a Ctrl-drag
— contradicting the rule that rotation survives zoom resets. It now carries `r` on
`CtrlZoomStart` and returns it.

## The Lightbox defects the v1 comparison exposed — and what the parallel session had already fixed

Comparing against v1 turned up four real defects. When I went to fix them, one had already been
fixed by the parallel session while I was on Phase 1 — worth recording, because the lesson is
that a review of a moving tree has a shelf life.

- **A. There was no way to zoom out — fixed here.** `MIN_SCALE = 1`, so pinch-apart and
  `Ctrl`+wheel-up were _live but inert_: they computed a value, clamped it straight back to 1,
  and nothing moved. v1 clamps to `[0.5, 8]` with exactly this in its comment. Now `0.5…5`.
  The subtlety worth writing down: **`MIN_SCALE` is not the definition of "resting"**. With a
  0.8 image now reachable, `scale > 1.01` and `scale > MIN_SCALE` mean different things, and
  only the first is right — a sub-fit image must centre and refuse to pan, exactly like a 1.0
  one. Added `REST_SCALE` / `REST_EPSILON` / `isAtRest()` to the engine and replaced the
  remaining hardcoded `1.01`s so the rule has one owner.
- **B. `onpointercancel={onPointerUp}` — fixed here.** A cancelled gesture ran the whole
  completion path. Marking a photo is a **server write**, so an incoming call or an edge-back
  mid-swipe could commit a vote, start a download or open the menu. v1 handles `touchcancel`
  separately for exactly this. Now `onPointerCancel`: drop state, snap the rotation to a resting
  angle, return the transform un-animated (nothing completed, so nothing settles).
- **C. The clamp measured the previous frame — already fixed** by the parallel session's
  `commitZoom` / `clampSettled`. I did extend it to the pinch end, which still clamped _before_
  writing: `snapRotation` moves the box's edges by tens of pixels, so clamping against the
  pre-snap rect is how the image settled out of frame at an angle it was no longer drawn at.
- **D. `Ctrl`+wheel zoomed about the stage centre — fixed here**, routed through `zoomToPoint`
  with the cursor as the anchor. A wheel that zooms about the centre slides whatever sits under
  the pointer toward the middle on every tick, so the detail you were scrolling toward never
  stayed put.

Still worth knowing from the same read: v1 pins `transform-origin: 50% 50%` explicitly and
explains why it must never be back-computed from an already-transformed rect — ours relies on the
default implicitly, which is fine but should stay deliberate. v1 also hides the volume button
during a drag; we don't.

Where v1 is **worse**, do not port it: it uses Touch events and needs
`state._suppressMouseUntil` plus `preventDefault()` chains to stop the browser synthesising
mouse events from a touch (Pointer Events, which we already use, have no such problem), and its
four-way classification is more convoluted than ours for the same result.

## Four interaction defects (user-reported, fixed same day)

1. **The up-gesture hint never collapsed.** `triggerGesture`'s `up` branch was the only direction
   without a timer, so `gestureDir`/`gestureRatio` were never cleared and the dragged hint stayed on
   screen behind the sheet. Now cleared before the sheet opens.
2. **Ctrl+drag flung the card off-screen.** `clampPan` required "no gap left AND no gap right", which
   can never both hold when the media is smaller than the stage, so one call pinned it bottom-right.
   Replaced with half-the-overflow per axis, centring anything smaller. Also fixed the ordering:
   write the transform, then read the fresh rect, then clamp (`clampSettled`) — clamping before the
   write measured the previous frame's already-legal geometry.
3. **Clicking the card paged like clicking the black mask.** After `setPointerCapture` on the stage,
   the click's `event.target` is always the stage, so `target.closest('.lb-box')` could never match
   the media. Switched to hit-testing with `document.elementFromPoint` (which respects the zoom
   transform); the media wrapper gained `data-lb-media`.
4. **A gesture mark sometimes did not auto-advance.** Not a math bug: the advance timer's `$effect`
   keyed on `photo?.sha256`, but Svelte 5 subscribes to the derived `photo` object itself. Marking
   replaces the photo entry in the store — same sha, new object identity — so the effect re-ran and
   its cleanup cleared the 200 ms timer. The second swipe did not write to the store, so it advanced.
   Keyed on `open` / `currentIndex` instead.

**Concurrent writer**: another-session process rewrote `Lightbox.svelte` every 10–15s during this
round (an unclosed brace was visible at one point). Its own output was good and was kept — it added
`MIN_SCALE = 0.5` (the zoom-out capability plus `isAtRest`/`REST_SCALE`) and fixed `pointercancel`
and the Ctrl+wheel anchor. Only one correction was needed here: `clampSettled` had an early
`isAtRest` return that stopped an 0.8 image from recentring.

## Another four Lightbox issues (same day, user-reported)

Double-click had no easing, the wheel did not zoom, Ctrl+drag could not rotate, and Ctrl could not be
pressed at will. Root causes and fixes:

1. **No easing on double-click zoom**: `zoomToPoint` → `commitZoom` never passed `animate`. Both
   gained an `animate` parameter; mouse `onDblClick` and the touch double-tap branch pass `true`.
2. **Wheel could not zoom**: `wheelZoom` began with `if (!e.ctrlKey) return`, blocking plain wheel.
   Gate removed; any wheel event zooms anchored on the cursor (a trackpad pinch arrives as
   Ctrl+wheel and takes the same path).
3. **Ctrl+drag could not rotate**: `ctrlZoomTransform` returned `rot: start.r` verbatim. Rewritten
   per the user's clarification — **the card centre is a fixed pivot**: the pointer's distance from
   it drives scale, its angle around it drives rotation, translate stays 0. `CtrlZoomStart` now
   carries `dist0`/`angle0`.
4. **Ctrl could not be pressed at will, and `Control` keydown reset the zoom**: deleted the
   `case 'Control'` reset; added `ctrlPressed` state plus `onkeyup`; pressing Ctrl mid-drag switches
   the plain drag into Ctrl mode via `beginCtrlZoom`. Releasing Ctrl does not exit — the gesture's
   type stays locked for the whole interaction.

Gate green: lint + ts-check + 90 tests. The Lightbox section of `.ai/CONTRACT.md` records all four.

## Rotation froze panning, and the Ctrl+drag snap was missing (same day)

The user reported "after rotating it can't be dragged", "where did v1's nearest-90° snap go", and
asked to adopt v1's double-click-to-restore.

- **Rotate-then-drag was frozen.** The pan gate was correct (`isRotated()` allows panning), but
  `clampPan` zeroed the offset whenever `isAtRest(scale)`, regardless of rotation. A pure rotation
  leaves `scale = 1`, so every move was clamped straight back to the centre. Now it force-centres
  only when at fit **and** unrotated; a rotated box is bounded by its own rotated-rect overflow.
  This is an improvement over v1, which also froze a purely-rotated image.
- **The 90° snap was missing on the desktop path.** `snapRotation` ran on pinch release but not on
  Ctrl+drag release, so a Ctrl rotation settled at an arbitrary angle. Added there too. Pinch and
  Ctrl now both snap to the nearest signed 90°.
- **Double-click-to-restore already matched v1** — `resetZoom(true, true)` returns to fit while
  keeping the explicit rotation. Verified rather than changed; recorded in CONTRACT.md so a later
  edit cannot quietly drop it.

Test added for the rotated-at-fit pan case (17 engine cases total). Gate green: lint + ts-check +
91 tests.

## Touch double tap was broken while the mouse worked (same day)

Reported as "移动端双击放大有问题（桌面端正常）". Two defects behind it, one commit (`e83cc4b`).

- **`classifyRelease` judged the pan before the tap** — the mobile-only one, and the reason the mouse
  hid it. Once zoomed, every single-finger touch is already a pan to `onPointerMove`, so the second
  tap of a double-tap could never reach the tap branch: double tap zoomed **in** (its first tap starts
  un-panned) and silently refused to zoom back **out** — only a pinch got you back. The desktop path
  is the native `dblclick`, which enters no state machine. The tap now precedes the pan, keyed on the
  release having travelled less than `TAP_SLOP`; a drag that genuinely moved is still a pan. v1 carries
  this exact ordering with a comment saying why; we had never ported it.
- **Every eased zoom clamped against a stale rendered rect** — shared with the mouse, just easier to
  miss there. Writes the transform and clamps in the same frame, before the transition has
  interpolated, so `getBoundingClientRect()` still described the _previous_ scale: the un-zoomed
  media, smaller than the stage, so all bounds collapsed to 0 and the anchor `zoomToPoint` had just
  computed was discarded. A double tap a quarter in from the left edge zoomed about the centre. The
  clamp now takes the wrap's **layout box** (`offsetWidth`/`offsetHeight` — transforms do not affect
  it) plus a new `rotatedBounds()` that scales and rotates it into the box it settles at.

**Verification method worth reusing.** Reproduced in the browser rather than by reading code, then
proved the fix by re-running the same script against `git checkout HEAD -- <src>`:

|                              | before                        | after                  |
| ---------------------------- | ----------------------------- | ---------------------- |
| pinch to 3×, then double tap | `scale(3)` — refused to reset | `scale(1)`             |
| double tap off-centre        | `translate(0px, 0px)`         | `translate(95px, 0px)` |

Three traps that each produced a false "it already works":

1. **CDP `Input.dispatchTouchEvent` cannot express which finger stays down**, so the pinch tail never
   happened and the old code passed. Synthetic `PointerEvent`s are what the component listens to;
   only `setPointerCapture` needs stubbing, via `addInitScript`.
2. Assertions can run **before the 200 ms auto-advance timer** fires, hiding a page-away.
3. The viewport has to be **phone-sized**: `scaledThreshold` makes the swipe threshold 30px at 390px
   wide and 100px on a desktop window, so desktop geometry cannot reproduce mobile misfires.

Landed as three cases in `web/tests/e2e/lightbox-pinch.spec.ts` including a desktop `dblclick` parity
case, so the two paths cannot drift apart. Gate: lint + ts-check + 96 web / 59 root tests.
