# 0012: Measured Bar Height Is Published Once, Consumed Everywhere

- **Date**: 2026-10-02
- **Status**: Accepted
- **Context**: ADR 0003 established that responsive state comes from measured values rather than breakpoints, and `topbarFit.ts` implements the top bar's density that way. The principle did not propagate past the bar's own controls, for two reasons. First, the bar's measured height was published as `--bar-h` on the `<header>` element only, so nothing outside the bar could read it — CSS inheritance stops at the bar, and any consumer had to guess. `AnnouncementEditorDialog.svelte` and `PollEditorDialog.svelte` both carried `top-14 md:top-16`, which is a breakpoint restating the bar's height endpoints (56px and 64px) as a range instead of reading the value. Second, `WaterfallLayout.svelte` re-derived the height itself with `barHeight(containerW)`, against the canvas width rather than the bar's width — a second copy of the ramp that could drift from the first. ADR 0003 names this as a follow-through trap ("whatever sits below must derive from that height rather than keep its own width formula"), and the layout had already been through repeated inset fixes (`b43b139`, `9c2d30c`).
- **Decision**: The bar publishes its measured height in one place, to two audiences. A new `state/barHeight.svelte.ts` holds `barHeightPx`, written by `TopBar.svelte` from the same `barH` that styles the bar, and the same effect sets `--bar-h` on `document.documentElement` so CSS consumers inherit it. Everything laid out beneath the bar reads that value: the waterfall canvas insets by `barHVar()`, and the admin editor dialogs offset by `top-[var(--bar-h,3.5rem)]` with a fallback for the window before the bar mounts. `WaterfallLayout` keeps `barHeight(containerW)` only as the pre-measurement fallback.
- **Consequences**:
  - One measurement, three consumers. Changing the ramp, its endpoints, or the hysteresis in `topbarFit.ts` moves the bar, the canvas inset, and the dialog offsets together; there is no second copy to update and no breakpoint to re-tune.
  - The dialogs' `top-14 md:top-16` disappears. `3.5rem` is a boot-time fallback, not a tuned value — it exists only so the first frame is not flush against the top edge, and it is replaced by the measured height as soon as the bar reports.
  - `--bar-h` on the root is also available to CSS that has no Svelte access, which keeps the variable and the state object from drifting: both are written from the same effect, in the same order, with the same value.
  - The measured height is now global state, so a consumer outside the bar's subtree couples to the bar's existence. The `barHVar(fallback)` shape makes that explicit — a consumer states what it does before the first measurement rather than silently reading 0.
- **Alternatives considered**:
  - _Keep `--bar-h` on the header and have consumers read it through a portal or a shared context_: rejected — CSS variables do not inherit into a sibling subtree, so this needs a JavaScript channel anyway, and the root element is that channel without the ceremony.
  - _Let each consumer call `barHeight()` with the width it has_: rejected — this is what the waterfall was doing. Two widths (bar and canvas) mapped through one ramp produce two heights that agree only by coincidence, and the symptom of divergence is an inset that is off by a few pixels at some viewport widths.
  - _Express the dialog offsets as breakpoints again, tuned to the measured range_: rejected — that is the existing code, and it re-encodes a measured value as a viewport question.
  - _Publish the height only as a CSS variable and let the waterfall read it with `getComputedStyle`_: rejected — not reactive in Svelte, so the canvas would need a resize listener to notice the change, which is a manual version of the same propagation the state object gives for free.
