# 0014: Transcode Output Streams Straight to OPFS, and a Hidden Page Keeps Its Lease

- **Date**: 2026-10-03
- **Status**: Accepted
- **Context**: Two problems surfaced from the same area. First, the encoder materialised its whole output before anything else happened: the video/GIF worker used mediabunny's `BufferTarget`, then wrapped the finished buffer in a `Blob` (a second full copy) and posted it across threads, so peak memory was about twice the artifact — up to 200 MB against the 100 MB upload cap, and mediabunny's own documentation marks `BufferTarget` as unsuitable for large files. Second, that shape forced a phase boundary: `onVideoResult` entered a separate `hashing` phase, cleared the progress fraction, and then reported byte progress from zero, so a row appeared to finish, blank out, and restart. Separately, the lease reaper revoked a lease after 15 s without a heartbeat, but a hidden document's `setInterval` is throttled to roughly one tick a minute, so switching tabs during a long encode discarded the finished work and restarted it — contradicting the lease client's own stated intent that a hidden page has not unloaded.
- **Decision**:
  - The page-side video worker writes its artifact through `openArtifactSink` (`web/src/transcode/opfs.ts`): a positioned `WritableStream` handed to mediabunny's `StreamTarget`, which is documented as compatible with `FileSystemWritableFileStream` and propagates backpressure to the encoder. The same write path feeds an incremental hash-wasm SHA-256, so encoding, hashing, and the OPFS write are one pass at O(chunk) memory instead of O(artifact).
  - `videoResult` carries `sha256` and `bytes` instead of a `Blob`. The `frames → hash → store` chain inside the SharedWorker is gone: the video path no longer has a `hashing` phase, and its single measured progress spans encode, mux, write, and digest. The image path keeps `storeArtifact` (a `Blob`) because `canvas.convertToBlob` has no streaming form.
  - Because a sink accumulates the digest only while each chunk continues the byte stream it has already seen, a muxer that seeks back to back-patch a header invalidates it. The sink detects that and falls back to hashing the finished file; the digest is never taken from an out-of-order accumulation.
  - A partially written artifact now exists on disk while encoding. Abandoning a job therefore requires releasing the handle: the page asks the worker to abort (`abortJob` → `aborted`) before terminating it, and the SharedWorker deletes the artifact on lease revocation and on dropping a dead owner's job.
  - Lease liveness becomes visibility-aware. The page reports `leaseVisibility` on grant and on `visibilitychange`; the reaper keeps the 15 s heartbeat timeout for a visible page but only retires a hidden lease once its port has been silent past the 120 s dead-owner threshold. Hiding never releases a lease. The listener belongs on the document, where the Page Visibility spec fires the event.
  - The lease client tracks every lease the page holds (`leaseId → jobId`) and heartbeats all of them from one timer; `release(jobId)` returns one job's token and `release()` returns them all. The pool grants two or more leases to a single page, so a one-slot client starved every lease but the newest: the SW reaped the silent one after 15 s and re-encoded that job from zero, and the following grant starved the other, so two concurrent video jobs ping-ponged indefinitely. That starvation, not the hashing phase, is what a row "resetting and restarting from 0" actually was.
- **Consequences**: Peak memory during a large encode no longer scales with the artifact, and a row's progress is monotonic because there is no phase boundary to reset. Switching tabs no longer throws away a finished encode, and two concurrent video jobs no longer starve each other's lease. The costs are real: the artifact exists in a partial state during encoding, so every abandonment path must abort the stream and delete the file, and artifact IO is no longer owned solely by the SharedWorker — a page worker now writes into the same OPFS directory. A worker killed without completing the handshake relies on the SharedWorker's deletion as a backstop.
- **Alternatives considered**:
  - _Keep `BufferTarget` and only fix the phase reporting_: rejected because it leaves the memory peak and the second full copy in place, and the phase boundary would still need an invented composite progress value to hide the reset.
  - _`AppendOnlyStreamTarget`_: rejected because it throws at runtime for formats that do not write strictly sequentially, and the type definitions cannot confirm WebM qualifies — a failure that would only appear in a browser.
  - _Stream the write but hash by reading the file back every time_: rejected because the extra pass is only needed for a back-patching muxer; the ordered fast path covers the normal case and the read-back stays as the correctness fallback.
  - _Raise `LEASE_TIMEOUT_MS` to cover background throttling_: rejected because it weakens crash recovery for every visible page; keying on document visibility targets the actual cause.
