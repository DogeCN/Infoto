# 0016: The Op Log Supersedes Writes That Only Have a Last Value

- **Date**: 2026-10-07
- **Status**: Accepted
- **Context**: The op log was append-only, so a user who toggled a like five times, changed a poll vote three times, or re-picked a reaction queued one op per interaction. Every one of those ops is sent, applied, and cleared. The cost is real but modest: a larger request body, more server work, and — the sharp edge — a larger `pagehide` keepalive prefix, which is capped at 65 536 bytes, so a long queue of redundant ops can push a genuine edit past the budget and lose it with the tab. The op count is also what the pending badge shows, so the user watches it climb for edits that have no distinct effect.
- **Decision**:
  - An op that writes a dimension the server resolves last-write-wins may **supersede** a queued op on the same dimension instead of appending. `coalesceKey` names those dimensions: a photo's **attitude** (`like`, `unlike`, `dislike`, `undislike`), its reports (`report`/`unreport`), a poll vote per voter, and a reaction per announcement and voter. `upload`, `delete` and `fb_create` have no key — they are ordered, terminal, or append-only.
  - **The server owns the like/dislike exclusion, which is what makes one attitude dimension possible.** Adding either clears the other column in the same statement that writes the mark, so a client states a switch with one op and needs no paired removal; and because the clear is symmetric, the newest op states the whole intent. Before this the exclusion was a client convention: `toggleMark` emitted `undislike` + `like` to keep "either, never both", two ops for one choice, and a client bug could write a row carrying both. Reports stand alone and may coexist with either attitude, so they keep their own dimension.
  - The superseded entry is **replaced in place** (`putOp`, same key), not removed and re-appended. Its position in the log is part of the contract: a mark must follow the upload op that creates its row.
  - An op already claimed by an in-flight request is **never** superseded. That request carries the old value, and a successful response clears the key, so replacing it would delete the replacement too — a silently lost edit. A superseding op is appended instead, and the server's last-write-wins ordering absorbs it.
  - Coalescing is the engine's, not the caller's: `addOp` decides, so every write path gets it and no caller has to know which ops are reducible.
- **Consequences**: A queued dimension holds at most one op, so repeated toggling costs one entry and the pending badge describes distinct work. The keepalive prefix carries more real edits. A switch between like and dislike is one op instead of two, and the local fold mirrors the server's clear so an optimistic row never disagrees with the snapshot that follows it. The op log stops being a faithful interaction history — it is now a _state_ log, and `reapplyQueued` already treats it that way (it folds ops into state rather than replaying a history). The scan that finds the superseded entry runs only for ops that have a dimension, so a batch of uploads never pays for it; it is linear in the queued op count, which every sync trigger drains. The in-flight exclusion is load-bearing and is asserted, as is the server's exclusion.
- **Alternatives considered**:
  - **Dropping a pair that cancels out** (`like` then `unlike` → nothing) was rejected: an op whose response was lost may have landed, and dropping both abandons the correction. Keeping the last op is correct whether or not the earlier ones landed, so `like`+`unlike` collapses to `unlike`, never to nothing.
  - **Compacting only when building a batch** fixes request size but not the badge or the keepalive prefix, and leaves the log inflated between triggers.
  - **A new server-side set-state op** (`mark {like, dislike}`) was the first answer to the column switch and was rejected in favour of the above: clearing the opposite column in the existing statement needs no new op type, no new wire shape, and no version negotiation, and it upgrades the exclusion from a client convention to a server guarantee at the same time.
  - **Leaving the exclusion to the client and only coalescing within a column** was rejected: it keeps two ops for one choice, and it leaves the invariant breakable by any client that forgets the paired removal.
  - **Reordering ops server-side by dependency** would remove the need for the client-side ordering guarantee, but breaks the documented "applied strictly in array order" contract that the whole op layer rests on.
