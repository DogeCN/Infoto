# 2026-10-26

## 一次 200 张上传把 `/sync` 拖死，两个独立根因

用户报的现象：一次上传约 200 张，页面显示"同步中"后卡死；刷新之后瀑布流空空如也，但照片
其实已经上传成功并托管了。截图给了两条硬证据：`POST /sync` 的 `Content-Length: 61962`
（≈200 条 upload op，远低于 `MAX_SYNC_OPS = 500`），状态 `NS_BINDING_ABORTED`；Cookie 里已有
`uuid=`，所以身份/Turnstile 不在关键路径上（上一轮我猜 Turnstile 是错的）。

### 根因一：`applyOps` 是逐条串行 await，200 条 op ≈ 400 次 D1 往返

`upload` 每条先 `SELECT id FROM photos WHERE sha256 = ?` 查重，再 `INSERT`；mark/delete 先
`resolvePhotoId` 再写。这些语句本身不慢——用 `node:sqlite` 原样回放同样的序列是 0.6 ms /
200 条——慢的是**每次 D1 往返**。按 20–30 ms 算，400 次就是 8–12 s，还要再叠一次全表快照
（199 张照片，59.5 KiB）。客户端的 15 s 预算先到，于是请求被中止，`clearKeys` 不执行，整批
op 留在 IndexedDB 里等下一次触发（而本项目规定同步只能由显式操作/页面打开/pagehide 触发）。

修法（ADR 0023）：校验全部放在 JS 里，`planOp` 把每条 op 变成 1–2 条 `DbStatement`，**一律
按 sha256 寻址**（唯一索引，所以不需要先查行）：upload 变成一条条件插入
`INSERT … SELECT … WHERE NOT EXISTS`，mark 一条 `UPDATE … WHERE sha256 = ?`，delete 一条
`DELETE … WHERE sha256 = ?`，react 的存在性检查塞进插入的 `WHERE EXISTS` 里。计划按 op 顺序
落进 `db.batch`，每次事务 `MAX_BATCH_STATEMENTS = 100` 条语句。唯一的预读是这批 op 要投票的
poll 定义——它是管理员接口创建的，任何 sync op 都改不了它，所以提前读是安全的。

跨 chunk 的顺序是承重的：一条 mark 跟在"创建它那行"的 upload 后面时必须仍然生效，测试
`ops keep their order across a chunk boundary` 就是钉这个的。失败隔离从"每条 op"变成"每个
chunk"——JS 校验保证坏 op 进不了事务，所以能失败的只有基础设施。

### 根因二：乐观卡片是内存态，刷新后 ops 变隐形

`uploadTasks` 是 `$state(new Map())`；SharedWorker 在上传成功时**主动删掉** resume 记录（注释
写明了原因：留着会让下次加载重复上传、重复写 op）；终态的 OPFS 产物又被
`reclaimTerminalJobs` 每 15 s 裁到最近 30 个。所以 200 张的批次里，刷新后唯一还活着的痕迹就是
那条 `upload` op——而它从来没被任何界面读过。

修法（ADR 0024）：op log 从"只写队列"变成**渲染来源**。`queuedUploadFromOp` /
`queuedUploadCards`（纯函数，`core/pending.ts`）把未确认的 upload op 投影成卡片，媒体用
`payload.url`（facade 返回的托管 URL，也就是相册自己的字节），**不用 OPFS 产物**——op 里没有
`jobId`，产物也不够用。读取时机只有两个：页面打开、同步尝试结束；都是读，不是触发器
（ADR 0008 的触发清单不变）。

三个坑：

- **卡片必须没有覆盖层。** 这张卡片没有任何可测量的进度，把幕布停在 `CURTAIN_MAX_OPEN = 0.9`
  会变成一条永久的 10% 进度条。所以它长得和 `done` 阶段的卡片一样：干净媒体、无幕布、无控件。
- **去重要两道。** 一道是既有的 landed-sha 守卫（快照里有这个 sha 就不画卡片），一道是对活跃
  task 的 sha 去重；否则同步成功那一帧会同时出现真照片和卡片。
- **删除需要会话级抑制集合。** `buildUploadOp` 写的是 `{ type: 'upload', target: null,
payload }`——**没有 `targetSha`**，而 `removeOpsBySha` 只按 `targetSha` 匹配，所以它根本撤不
  掉 upload op 本身（文档此前说"撤回 upload + mark ops"，是错的，本次一并改正）。删掉的卡片
  靠 tombstone 在服务端抵消；本地靠 `withdrawnShas` 阻止下一次读取把它画回来。

### 没验证到的部分（诚实记录）

生产上 `/sync` 带 200 条 op 的真实耗时没有实测到：curl 直连在鉴权那步就 401 早退了。
"400 次串行往返撑爆 15 s 预算"是代码结构 + 截图证据推出的结论；已修的是往返次数这个可测的
量（测试钉死为常数），而不是"某次请求耗时 X 秒"这个没测到的量。

### 遗留（本次故意不做）

`upload` op 不带 `targetSha`，导致删除一张待同步照片时撤不掉它的 upload op、只能靠 tombstone
在服务端抵消。修法是把 `targetSha` 加进 `buildUploadOp`（对服务端与 `coalesceKey` 都是惰性的），
但那会改动同步线上载荷，属于另一个维度，按 ADR 0015 应单独提交。

## 把六处存储收敛成「一张照片一条记录」

上一轮回答里说过 ops / OPFS / 元数据缓存有发散，这一轮按 ADR 0025 全做了。

### 收敛后的形状

- **3 个存储 + 字节**：`oplog`（唯一有序写队列）、`photos`（一张照片一条记录，keyPath = sha256）、
  `metaCache`（服务端快照）、OPFS（产物字节）。
- `jobId` 不再是任何存储的键：它只作为记录里的 `artifact.key` 活着。**唯一偏离"sha 是唯一持久键"
  的地方，原因是被写死的**：`storeArtifact` / `openArtifactSink` 是边写边算摘要，文件名必须先于摘要
  存在，改成 sha 命名就得为每张照片多读一遍字节。
- 消失的机制：`withdrawnShas`、投影里"按 sha 取日志最后一条 op"的 tombstone 规则、
  `pendingMarks`（localStorage）、`temp-created`（sessionStorage + 30 分钟 TTL）、
  `removeOpsBySha` 对 upload op 的按 sha 扫描。

### 关键的一步是原子性，不是合并

丢照片窗口的根因是**同一事实分两个存储、两次写**：SW 在 `done` 里先删 resume 记录再 `notify`，
页面收到才写 op。现在：

- worker 写 `uploading` / `failed`；
- **页面**把 `uploading → hosted` 和追加 upload op 放进同一个 `['oplog','photos']` 事务；
- engine 在快照折叠进 store 之后才删记录（记录的 marks 正是 `applySync` 要落成 op 的东西）；
- 删除是一个事务：记录 + 该 sha 的 mark op + 记录拥有的那条 upload op（按 `opKey`），
  tombstone 仍然保留，只为覆盖"op 已被在途请求带走"。

### 升级取舍

`DB_VERSION` 2→3：只新增 `photos`、不加改动 `oplog`/`metaCache`（队列原样保住），删除
`pendingUploads`；`pendingMarks`/`temp-created` 不再被读。按红线 1 不做兼容垫片：升级瞬间在途的
上传不再续传，未同步照片上的乐观标记丢失。

### 验证

- web 套件 146 个测试全绿（原 145，新增/重写覆盖记录生命周期）。
- 新增 `oplog.test.ts` 用例：op 与记录同事务写入、`opKey` 精确撤回、迟到写不复活。
- `pendingUploadCards.test.ts` 重写为真存储 + 真 engine：失败同步后记录仍在、成功同步后记录被回收、
  landed/live 去重、worker 自有的 `uploading`/`failed` 记录不画卡片。
- `resumeUpload.test.ts` 改为断言 `status: 'failed'` 与 `artifact.key`。
- 门禁：lint / ts-check / test / build 全绿。

### 审查本身的价值：235 个测试全绿时它找到的东西

- **策略值没有测试就会漂。** `COOKIE_MAX_AGE = 345_600_000` 秒（4000 天），而两行之上的注释写着
  「400 天是浏览器接受的上限」。数字和注释都像权威，只有缺一条断言能让它们差 10 倍。已改为
  `34_560_000`，并在 `sync.test.ts` 断言 `Max-Age=34560000`。→ MEMORY「Adversarial Review」节。
- **`sed` 改不动也退出 0。** `deploy.yml` 的三处 `s` 命令在锚点失效时静默无操作：tag 推送会用
  仓库里的 `infoto-dev` 名字部署生产。现在三处都回读校验，不匹配即 `::error::` 退出。
- **闸门比自己描述的弱。** schema 闸门折叠了空白并小写化两侧，而三份文档都说 byte-identical；copy
  键闸门只匹配叶子词（`download` 能命中 Markdown 的 `download` 属性），删掉整个调用点仍然通过。
  前者改为「只归一化行尾」的比较，后者改为「必须以键路径结尾的成员链」并排除 `*.test.ts`。
- **两处派生到第四处才开始分叉。** 产物扩展名有 4 处派生（3 种输入），mark→列映射有两份（加第四个
  mark 种类会在回收时静默丢失），投票选项规则有三份且行为不同（过滤 vs 拒绝）。都收敛到一处。
- **不能失败的测试比没有更糟。** 两例是自比较（`ceil(x) >= x`、`easing === easing`），一例对着
  测试内部声明的常量断言几何值；三者对任何输入都通过。已删除或改成真断言。
- **视频置换 `src` 会打断播放（用户报告，未复现）。** 机制是 `pendingMediaUrl` 在 hosted 就绪时把
  `<video>` 的 `src` 从 blob: 换成 https:，元素重载即停止播放；只在「上传完成后 hosted 预取那几秒内
  打开 pending 视频」的窗口内成立。用户表示无法稳定复现，因此**不改行为**，只记录机制与窗口。

### 本轮确定的口径（不是顺手改）

- **单元用例数目标取消。** 原文「keep the unit suite under 100 cases」被违反到 235 例，而唯一一次
  执行它（`ec40dbd`，208→49）把 `topbarFit` 的 20 例砍成 2 例，同一文件记录那次损失是真实的。
  新规则：一个用例是一份契约，不是预算；只在「同一所有者的同一失效模式」下合并，靠整合而不是删减
  控制规模。文件按所有者归并：`photoRecords.test.ts` 吸收 pendingPhoto / uploadPhotosOps /
  uploadPreview 三个文件（4 文件 → 1，19 例 → 19 例，一例保留并注明与另一例同源）。
- **`selectAll` 保留「选中全部卡片」的既有语义。** CONTRACT §3 明文记录：失败的上传也要能被批量
  选中，那是卡住的上传的出路。因此不改 `selectAll` 的覆盖范围，改的是 `MultiSelectBar` 的
  `allSelected`：它原先把「已选数」和「hosted 计数」两个集合相比，屏幕上只要有 pending 就永远
  「未全选」，再点一次是重新选中而不是清空。现在与「屏幕上的全部卡片」相比，尺寸/下载仍只算 hosted。
- **pending 卡片并入唯一过滤/排序管线。** 原先 `[...pending, ...photos]` 直接前置，绕过筛选与排序
  （`latest` 升序时最新一张仍在最上）。现在一个数组走同一个 `applyFilters` + `sortPhotos`，

- **设置 blob v5。** 新增 `playback.volume`（0–1，默认 1）；v4 blob 整体丢弃，不做逐字段迁移

## Lightbox 手势：取消平移边界、Ctrl 不再回中心、滚轮加缓动

用户报的现象：Lightbox 里按 Ctrl 会把图片重置到中心；放大或旋转后拖动被限制；双击放大后同样受限制；
滚轮缩放没有缓动。另一个"从瀑布流进入时图片莫名平滑放大"不稳定复现，按用户指示先放弃（代码里没找出成因）。

### 改动

- **平移无边界。** 删除 `clampPan` / `rotatedBounds` / `isZoomedBeyondViewport`，新增 `settlePan`：只有
  "处于 fit 且未旋转" 才归中，其余状态原样保留偏移。旧 clamp 把偏移限制在半溢出内，旋转图的两轴溢出
  本来就只有几像素，拖动很快"到头"——这正是用户感到的限制。
- **Ctrl 以媒体自身中心为轴。** `CtrlZoomStart` 增加 `x`/`y`，`ctrlZoomTransform` 原样返回；组件
  `beginCtrlZoom` 不再把 `zoomX/zoomY` 清零，因此在已平移/放大的图上按 Ctrl 不会跳回舞台中心。同时允许
  在拖动中或平移中按 Ctrl 进入该模式（原来 `!panning` 才会切换）。
- **判据从"渲染框溢出"改为 `isPannable`（`!isAtRest(scale) || isRotated(rot)`）。** 轻度放大（例如 1.2×，
  仍小于舞台）现在拖动是平移，不再被当成 swipe 去点赞/翻页。
- **滚轮缩放加缓动。** `wheelZoom` 改传 `animate=true`，与双击共用 `applyWrap` 的 transform transition
  （`--duration-exit`）；连续 tick 从插值帧 retarget，保持连续。
- `zoomToPoint` 落到 fit 时也只在未旋转时清偏移，否则旋转的 fit 视图会把用户拖出来的位置丢掉。

### 验证

- `lightboxEngine.test.ts` 重写 clamp 段为 `settlePan`/`isPannable` 用例，17 例全绿；`npm test` 91 + 142 全绿，
  `npm run lint`、`npm run ts-check` 全绿。
- 新增 e2e `web/tests/e2e/lightbox-gestures.spec.ts`（4 例）：放大后拖动保留完整位移（旧 clamp 会截断）、
  双击放大后同样能拖过旧边界、Ctrl+drag 旋转后平移量不变、1.2× 拖动为 pan 且不产生标记。
- 首轮 13 个 lightbox 相关 e2e 有 9 个通过后中断：另一个进程在 `web/src` 下写入临时文件让本地 Vite
  触发 `EBUSY: resource busy or locked, watch` 崩溃，余下 4 个是 `ERR_CONNECTION_REFUSED`。并发写停止后

### 用户追加的三项（同日，同一发版）

- **复制确认改成原地反馈**：建议条目的复制按钮成功时不弹 toast，按钮内的图标在同一 16px 格子里交叉淡出/淡入成勾，按钮进入 active 态，`COPIED_HOLD_MS = 1600` 后淡回。失败仍走 `lightbox.copyFailed` 的 toast。原因：确认应该出现在点击落下的地方，而不是屏幕角落。
- **乐观上传卡片插到最前**：`App` 用 `[...pending(createdAt 倒序), ...sortPhotos(applyFilters(hosted))]`，即 pending 卡片始终在最前、且**不参与**筛选与排序。上一轮把它们并入同一条排序管线，导致升序/随机/热度排序时新卡片跑到末尾甚至被筛选隐藏。CONTRACT §3 已按此改写（保留「批量删除卡住的上传」与「尺寸/下载只算 hosted」两条）。
- **移动端渲染长相册闪退 → 媒体带宽小于渲染带宽**：`<img>` 在文档中会按**原始尺寸**持有解码位图（12MP ≈ 48MB），渲染窗口是 5 个视口（为滚动流畅），两者相乘就是闪退来源。现在卡片只在「视口 ±0.4 视口」内持有媒体元素（`MEDIA_LOAD_LOOKAHEAD`），离开即移除元素并清 `loadedUrl`，销毁的 `<video>` 暂停并解绑 `src`。渲染窗口不变。**残留风险**：单张超大原图仍按原尺寸解码——部署里没有缩图服务，真正的上限是在转码时限制长边，属于产品决定，已记在 CONTRACT §3 与 MEMORY。
- **并入一份并发会话的改动并单独审查**：`lightboxEngine` 的平移模型被整体替换——`clampPan`/`rotatedBounds`/`isZoomedBeyondViewport` 删除，改为 `settlePan`（只在贴合且未旋转时归中）+ `isPannable`（缩放或旋转即可平移），Ctrl 手势改为围绕媒体自身中心并沿用当前平移；配套重写了 17 例引擎测试、更新了 CONTRACT §3/§5、新增 e2e `lightbox-gestures.spec.ts`。审查结论：自洽、门禁全绿、契约同步更新；保留并计入本次发版。
- 发版口径由用户改为 **MINOR**（0.3.6 → 0.4.0），因为本轮含两个新控件与两个行为变更。
