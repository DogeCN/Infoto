# 2026-10-26

## 一次 200 张上传把 `/sync` 拖死，两个独立根因

用户报的现象：一次上传约 200 张，页面显示"同步中"后卡死；刷新之后瀑布流空空如也，但照片
其实已经上传成功并托管了。截图给了两条硬证据：`POST /sync` 的 `Content-Length: 61962`
（≈200 条 upload op，远低于 `MAX_SYNC_OPS = 500`），状态 `NS_BINDING_ABORTED`；Cookie 里已有
`uuid=`，所以身份/Turnstile 不在关键路径上（上一轮我猜 Turnstile 是错的）。

### 根因一：`applyOps` 是逐条串行 await，200 条 op ≈ 400 次 D1 往返

`upload` 每条先 `SELECT id FROM photos WHERE sha256 = ?` 查重，再 `INSERT`；mark/delete 先
`resolvePhotoId` 再写。这些语句本身不慢——用 `node:sqlite` 原样回放同样的序列是 0.6 ms /
200 条——慢的是**每次 D1 往返**。按 20–30 ms 算，400 次就是 8–12 s，还要再叠一次全表快照
（199 张照片，59.5 KiB）。客户端的 15 s 预算先到，于是请求被中止，`clearKeys` 不执行，整批
op 留在 IndexedDB 里等下一次触发（而本项目规定同步只能由显式操作/页面打开/pagehide 触发）。

修法（ADR 0023）：校验全部放在 JS 里，`planOp` 把每条 op 变成 1–2 条 `DbStatement`，**一律
按 sha256 寻址**（唯一索引，所以不需要先查行）：upload 变成一条条件插入
`INSERT … SELECT … WHERE NOT EXISTS`，mark 一条 `UPDATE … WHERE sha256 = ?`，delete 一条
`DELETE … WHERE sha256 = ?`，react 的存在性检查塞进插入的 `WHERE EXISTS` 里。计划按 op 顺序
落进 `db.batch`，每次事务 `MAX_BATCH_STATEMENTS = 100` 条语句。唯一的预读是这批 op 要投票的
poll 定义——它是管理员接口创建的，任何 sync op 都改不了它，所以提前读是安全的。

跨 chunk 的顺序是承重的：一条 mark 跟在"创建它那行"的 upload 后面时必须仍然生效，测试
`ops keep their order across a chunk boundary` 就是钉这个的。失败隔离从"每条 op"变成"每个
chunk"——JS 校验保证坏 op 进不了事务，所以能失败的只有基础设施。

### 根因二：乐观卡片是内存态，刷新后 ops 变隐形

`uploadTasks` 是 `$state(new Map())`；SharedWorker 在上传成功时**主动删掉** resume 记录（注释
写明了原因：留着会让下次加载重复上传、重复写 op）；终态的 OPFS 产物又被
`reclaimTerminalJobs` 每 15 s 裁到最近 30 个。所以 200 张的批次里，刷新后唯一还活着的痕迹就是
那条 `upload` op——而它从来没被任何界面读过。

修法（ADR 0024）：op log 从"只写队列"变成**渲染来源**。`queuedUploadFromOp` /
`queuedUploadCards`（纯函数，`core/pending.ts`）把未确认的 upload op 投影成卡片，媒体用
`payload.url`（facade 返回的托管 URL，也就是相册自己的字节），**不用 OPFS 产物**——op 里没有
`jobId`，产物也不够用。读取时机只有两个：页面打开、同步尝试结束；都是读，不是触发器
（ADR 0008 的触发清单不变）。

三个坑：

- **卡片必须没有覆盖层。** 这张卡片没有任何可测量的进度，把幕布停在 `CURTAIN_MAX_OPEN = 0.9`
  会变成一条永久的 10% 进度条。所以它长得和 `done` 阶段的卡片一样：干净媒体、无幕布、无控件。
- **去重要两道。** 一道是既有的 landed-sha 守卫（快照里有这个 sha 就不画卡片），一道是对活跃
  task 的 sha 去重；否则同步成功那一帧会同时出现真照片和卡片。
- **删除需要会话级抑制集合。** `buildUploadOp` 写的是 `{ type: 'upload', target: null,
payload }`——**没有 `targetSha`**，而 `removeOpsBySha` 只按 `targetSha` 匹配，所以它根本撤不
  掉 upload op 本身（文档此前说"撤回 upload + mark ops"，是错的，本次一并改正）。删掉的卡片
  靠 tombstone 在服务端抵消；本地靠 `withdrawnShas` 阻止下一次读取把它画回来。

- `web/tests/unit/pendingUploadCards.test.ts`（新）：失败的 sync 之后 op 仍然投影成卡片；

- `web/tests/unit/pendingPhoto.test.ts`、`syncEngine.test.ts`、`uploadPreview.test.ts` 各自补了

  它拉进 SharedWorker bundle）。
- `npm run lint` / `npm run ts-check` / `npm test` 全绿。
- 浏览器里的实测（headless Edge + 本地 dev 栈，`/sync` 由 Playwright 拦断以复现超时）：先建立

  媒体实测 `naturalWidth × naturalHeight = 800×600`、卡片盒子 178px——是真画出来的卡片，不是
  空盒子；随后放开同步再触发一次，3 张卡片随 op 一起消失，oplog 归零。before 就是用户截图里的

### 没验证到的部分（诚实记录）

生产上 `/sync` 带 200 条 op 的真实耗时没有实测到：curl 直连在鉴权那步就 401 早退了。
"400 次串行往返撑爆 15 s 预算"是代码结构 + 截图证据推出的结论；已修的是往返次数这个可测的
量（测试钉死为常数），而不是"某次请求耗时 X 秒"这个没测到的量。

### 遗留（本次故意不做）

`upload` op 不带 `targetSha`，导致删除一张待同步照片时撤不掉它的 upload op、只能靠 tombstone
在服务端抵消。修法是把 `targetSha` 加进 `buildUploadOp`（对服务端与 `coalesceKey` 都是惰性的），
但那会改动同步线上载荷，属于另一个维度，按 ADR 0015 应单独提交。

## 把六处存储收敛成「一张照片一条记录」

上一轮回答里说过 ops / OPFS / 元数据缓存有发散，这一轮按 ADR 0025 全做了。

### 收敛后的形状

- **3 个存储 + 字节**：`oplog`（唯一有序写队列）、`photos`（一张照片一条记录，keyPath = sha256）、
  `metaCache`（服务端快照）、OPFS（产物字节）。
- `jobId` 不再是任何存储的键：它只作为记录里的 `artifact.key` 活着。**唯一偏离"sha 是唯一持久键"
  的地方，原因是被写死的**：`storeArtifact` / `openArtifactSink` 是边写边算摘要，文件名必须先于摘要
  存在，改成 sha 命名就得为每张照片多读一遍字节。
- 消失的机制：`withdrawnShas`、投影里"按 sha 取日志最后一条 op"的 tombstone 规则、
  `pendingMarks`（localStorage）、`temp-created`（sessionStorage + 30 分钟 TTL）、
  `removeOpsBySha` 对 upload op 的按 sha 扫描。

### 关键的一步是原子性，不是合并

丢照片窗口的根因是**同一事实分两个存储、两次写**：SW 在 `done` 里先删 resume 记录再 `notify`，
页面收到才写 op。现在：

- worker 写 `uploading` / `failed`；
- **页面**把 `uploading → hosted` 和追加 upload op 放进同一个 `['oplog','photos']` 事务；
- engine 在快照折叠进 store 之后才删记录（记录的 marks 正是 `applySync` 要落成 op 的东西）；
- 删除是一个事务：记录 + 该 sha 的 mark op + 记录拥有的那条 upload op（按 `opKey`），
  tombstone 仍然保留，只为覆盖"op 已被在途请求带走"。

### 升级取舍

`DB_VERSION` 2→3：只新增 `photos`、不加改动 `oplog`/`metaCache`（队列原样保住），删除
`pendingUploads`；`pendingMarks`/`temp-created` 不再被读。按红线 1 不做兼容垫片：升级瞬间在途的
上传不再续传，未同步照片上的乐观标记丢失。

### 验证

- web 套件 146 个测试全绿（原 145，新增/重写覆盖记录生命周期）。
- 新增 `oplog.test.ts` 用例：op 与记录同事务写入、`opKey` 精确撤回、迟到写不复活。
- `pendingUploadCards.test.ts` 重写为真存储 + 真 engine：失败同步后记录仍在、成功同步后记录被回收、

- 门禁：lint / ts-check / test / build 全绿。
