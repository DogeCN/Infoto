# 2026-10-07 — Deleting a pending upload actually deletes it

## The report

"未同步文件的删除没生效" — refined to: the photo became a **ghost card** that a reload
clears. Deleting an unsynced photo changed nothing on screen.

## Why

A pending card is the **upload store's** optimistic entry (`uploadTasks` → `pendingPhotos`),
not a row in the photo store. `deletePhotos` removed ids from `store.photos` (none exist for a
pending photo) and filed a `delete` op, but never touched the upload store — so the card sat
until a reload emptied `uploadTasks`. "Ghost until refresh" was the whole feature set.

Worse, and only visible after a sync: the oplog is append-only, so a delete filed while the
upload was still in flight appended as `[delete, upload]`. The server applies ops in order and
no-ops a `delete` whose sha matches no row (`resolvePhotoId` → null), then the `upload` creates
the row — the deleted photo landed for real.

## The fix

`deletePhotos` now splits on "does the store hold this sha":

- **Synced** — the old path: optimistic removal + a `delete` op.
- **Pending** — `withdrawPendingUpload`:
  1. the cancel sink aborts the job (an in-flight transfer dies before it can write its upload
     op; the SharedWorker drops its record and the OPFS artifact);
  2. `engine.removeOpsBySha` withdraws every queued op carrying that sha (upload + marks);
  3. a `delete` op is filed **last**, as the tombstone.

Ordering is load-bearing twice. The tombstone must come after the withdrawal because
`removeOpsBySha` matches by sha and would take it with it. And the tombstone must exist at all
because step 1 cannot close every race: an upload op already claimed by an in-flight sync
request cannot be un-sent. If that request lands, the tombstone deletes the row it created; if
it fails, the tombstone is a server no-op on an unknown sha. Either way the album ends correct.

## Wiring

`appStore` cannot import the upload store (circular), so the upload store registers a cancel
sink through `setPendingUploadCancelSink` — the second user of the pattern `setMediaHostSink`
established. `App.svelte` needed no change: both delete entry points (Lightbox, multi-select)
already go through `store.deletePhotos`.

## Verification

`removeOpsBySha` is covered twice (oplog: removes only the matching sha's ops, counts them,
no-ops on an absent sha; engine: pending count drops and the oplog keeps the others). The
store-level glue — the branch in `deletePhotos`, the sink, `cancelPendingBySha` — has no test:
`createUploadStore` needs a component context (`onDestroy`), and no appStore harness exists.
Recorded as a gap in CONTRACT §3, the same way `overlay.ts` is.

Unchanged by design: the media-host artifact is orphaned whenever a _synced_ photo is deleted
— the server's `delete` removes only the DB row, and the facade contract has no deletion
endpoint. Withdrawing a pending upload's ops is what avoids creating a row that would have to
be deleted; it cannot un-upload an artifact that already landed.

## A like on an uploading photo was silently lost

Operator question: can ops be made reversible (like→unlike, vote change) by editing the
original op, to cut op count? Investigating that surfaced a bug first.

`setMarkBySha` submitted its op immediately, while the upload op is written only once the
transfer completes. So the log read `[like, upload]`, and `/sync` applies a batch in array
order: `resolvePhotoId` finds no row for the sha, `setMark` returns on `photoId === null`, and
the upload then creates the row. The like is gone — and the op is cleared as confirmed, so
nothing can recover it. Liking a photo while its card still shows progress always lost the
like.

This is not new. `deferredPhotoOps` existed to prevent exactly this and was **deleted in
`eb1dd41`** (2026-09-27) in a commit whose message never mentions it. Its removal may have
been a bug fix rather than a regression: the old condition tested only `queuedUploadShas`,
which is populated when an upload op is written — so a mark on any photo that came from a
snapshot was deferred forever and never sent either. The restored version tests "the snapshot
does not carry the sha **and** no upload op is queued", and `photoOpQueued` is now awaited so
the released ops follow the upload op by construction, not by IndexedDB transaction ordering.

The other half of yesterday's tombstone race is closed in the same place: `onUploadOp` writes
nothing when no tracked task still owns the sha. Without it, a `done` notification arriving
just after a delete would append its upload op behind the tombstone — `[delete, upload]` again,
the photo lands, and the deleted photo reappears on the next snapshot.

## Coalescing: keep the last op per dimension, never drop a cancelling pair

Implemented per ADR 0016. The naive reading of "reversible ops" — like then unlike means no op
at all — is wrong: an op whose response was lost may have landed, and dropping both abandons
the correction. Keeping the newest op is correct either way, so `like`+`unlike` collapses to
`unlike`.

What collapses: the three mark columns per photo, a poll vote per voter, a reaction per
announcement and voter — the dimensions the server resolves last-write-wins. What does not:
`upload`, `delete`, `fb_create`, which are ordered, terminal, or append-only. A column switch
(dislike→like) is two ops in different columns and stays two; collapsing it would need a new
server op type.

Two implementation rules carry the safety: a superseding op replaces the queued entry **in
place** (same key, so it keeps its position behind the upload op), and an op an **in-flight
request already carries is never superseded** — that request holds the old value and a
successful response clears the key, so replacing it would delete the replacement too. Both are
asserted in `syncEngine.test.ts`; `coalesceKey` in `frontend.test.ts`; the deferral end to end
in `pendingPhotoOps.test.ts` (the first store-level test in this suite, made possible by
mocking `svelte-sonner`, whose dependency has no node export condition).

## The server now owns the like/dislike exclusion

The operator asked why a dislike→like switch cannot collapse like a vote change does. It can,
and the first answer here — "it would need a new server op type" — was wrong.

The blocker was that `setMark` wrote one column: `like` never touched `dislikes`, so the client
had to send `undislike` + `like` to keep "either, never both". That made the exclusion a
**client convention**, and it split one user choice across two coalescing dimensions.

Clearing the opposite column in the same statement that adds either fixes both at once: a
switch is one op, like and dislike share one `attitude:<sha>` dimension, and the invariant
becomes a server guarantee no client can break. The rule is symmetric on purpose — if only
`like` cleared `dislike`, collapsing `[like, dislike]` to `[dislike]` would leave the like
behind and be wrong. Only the _add_ side needs it: `unlike` and `undislike` cannot create
"both". Reports stay independent, as before.

`applyMarkToSet` mirrors the clear in the local fold. Without it the optimistic row would
disagree with the snapshot arriving right behind it — the fold has to speak the server's
semantics, not just the op's name.

Two things worth recording for the next reader:

- The deferral was **rebuilt while doing this**, not restored: the first version queued ops in
  memory (`deferredPhotoOps`), which diverges after a reload — `pendingMarks` is persisted, the
  op queue was not, so a reload during an upload left the card showing a like that would never
  be sent. The mark is now the source: `photoOpQueued` states the marks as ops, and `applySync`
  calls it for a row the snapshot has just delivered. No queue, and reload-proof.
- A wrong test expectation is worth chasing rather than adjusting: two assertions here failed
  because the other user's like/dislike was still in the column, not because the code was
  wrong. Chasing the second one led to checking whether `json_group_array` over an empty set
  returns NULL (it returns `'[]'`, so the removal path is fine) — and that path is now pinned,
  because the exclusion makes it run far more often.

## A guard meant for marks was silently eating every deletion

Chasing the operator's `derived_inert` warning (delete triggers it) I drove the real delete paths
in a browser — which surfaced a far worse bug I had introduced earlier the same day.

`submitPhotoOp` dropped any photo op whose sha was not in `photos` (correct for marks, which
need the row to exist). But `deletePhotos` removes the row optimistically **before** submitting,
so at submit time the sha is gone and the guard dropped the op. Every synced-photo deletion was
unqueued: the card vanished, nothing reached the log, no toast appeared, and the photo came back
with the next snapshot. Found because the oplog stayed empty after a delete that "worked".

Fixed by splitting the guard's scope: `submitMarkOp` keeps it, `deletePhotos` submits straight to
`submit`. A delete of an unknown sha is a server no-op, which is also exactly what the pending
photo's tombstone relies on. Regression test: `pendingPhotoOps.test.ts` deletes a snapshot photo
and asserts the op _is_ queued.

Also learned here: the local dev browser profile was **not root** (user 15), and both delete
entries are `{#if selfId === 0}`, so the delete UI could not be reproduced there at all. The
session cookie is HttpOnly, so it cannot be rewritten from the page; the operator's suggestion
(put the all-zeros uuid on user 0) gives a _settable_ dev root, and a page-level `fetch` patch on
`/sync` made this session root without touching the database.
